# 開発方針

手作業でルールを増やし続けるのではなく、複数の相手との対戦から方策と評価を継続的に
改善できる仕組みを作る。開発と局面確認は Mac、大量対戦と重み調整は Google Colab の
CPU で行う。

## 0. 実測で確認した制約

方針を立てる前に確かめた事実。ここが動くと設計も動く。

| | 確認内容 |
|---|---|
| Colab で動くか | `kaggle_environments/envs/cabt/cg/` に `libcg.so` (Linux x86_64) が同梱されている。Kaggle 本番も Linux なので、Colab のほうが Mac より本番に近い |
| 乱数シード | `cabt.json` にシード設定がなく、シャッフルとコイントスはネイティブ側。**対戦は再現できない** |
| SelectContext | `shared/enums.py` に 49 個の名前付き定数がある。文脈の意味は既知で、収集・分類の作業は不要 |
| Mac の並列度 | 8 論理コア (高性能 4 + 高効率 4)。現状 `-j 6` |
| Colab の並列度 | 未測定。標準ランタイムは 2 vCPU のことが多く、総スループットで Mac に負ける可能性がある |

**乱数シードが制御できないことの帰結**

- 学習用 / 検証用 / 最終評価用の分割は、シードではなく**デッキと方策プロファイルの組**で作る
- ペア比較による分散削減が使えないため、同じ検出力に必要な試合数が増える
- 再現性はシードではなく、全意思決定ログを残すことで担保する

## 1. 構成

4 要素に分ける。

- **ルールベース方策** — デッキ固有の基本動作と、明らかな悪手の回避
- **ロールアウト探索** — 候補を仮に実行し、その後の展開から比較する
- **相手モデル** — 公開カードから相手のデッキタイプと脅威を推定する
- **シミュレーション基盤** — 複数の相手・デッキ・先後で大量対戦し、改善効果を測る

初期はニューラルネットを入れない。ルールの重み、局面評価、対面別補正をシミュレーションから調整する。

## 2. 行動設計

### 2.1 フェーズ別の制御

局面を分類し、フェーズごとに優先順位を変える。

- **SETUP** — 進化元の確保、オーロンゲ ex を手札へ、Punk Up を活かせる進化、不要なベンチを埋めない
- **STABILIZE** — 攻撃可能な状態を作る、後続を準備する、エネルギーの過剰集中を避ける
- **PRESSURE** — きぜつを取れる攻撃を優先、主要アタッカーを識別、次ターンも攻撃を継続できる盤面を残す
- **DEFEND** — 被きぜつ確率を下げる、ベンチへの攻撃経路を減らす、相手の完成を妨害する
- **RECOVER** — オーロンゲ ex を失った後の後続、残り資源で実現可能な勝ち筋へ切り替える
- **CLOSE** — 残りサイドから最短の勝ち筋を計算し、勝てるターンは準備行動を省く

オーロンゲ ex の成立は切替点だが絶対条件にしない。即時のきぜつ、重大な被きぜつリスク、
ベンチ展開の危険があれば SETUP 中でも例外行動を許す。

段階的に入れる。いきなり 6 状態に分けず、既存のスコアに局面条件を足す形から始めて、
足りない部分が出てから状態機械にする。

### 2.2 選択文脈の区別

同じカードでも、評価の向きが文脈で変わる。評価単位は

    選択文脈 × カードID × 局面フェーズ × 相手タイプ

`SelectContext` は既知なので、向きは表で決められる。

    取得 (正) : ToActive ToBench ToField ToHand AttachTo Heal RemoveDamageCounter
    手放す(負): Discard ToDeck ToDeckBottom ToPrize DiscardEnergy DiscardEnergyCard
                DiscardToolCard DiscardCardOrAttachedCard ToDeckEnergy
    不明      : 価値表を適用しない。誤った知識を使うより中立へ戻す

## 3. 探索

### 3.1 役割分担

ルールベースは最終手を固定しない。ロールアウト中の不自然な行動を減らし、悪手を低く評価し、
標本の少ない根候補に弱い事前評価を与え、デッキ固有の展開を再現する。最終手は可能な限り探索で決める。

現状は根候補あたりの標本が少ないため、ルール評価を弱い事前値として入れる。

    Q_i = (Σr_i + λH_i) / (N_i + λ)

`H_i` は `[-1, 1]` に正規化する (生のスコアは 0〜200 程度なので、そのまま入れると λ=1 でも
ルールが探索を上書きする)。UCB の選択側にも入れる。λ は A/B で決める。

### 3.2 ロールアウト方策

ルールベースを原則とし、一定確率で別候補を選ぶ。自分と相手の双方に、それぞれのデッキに
合った方策を使う。60 手程度で打ち切り中間局面を評価する。UCB1 で配分し、候補差が明確に
なったら早期終了する。ランダム率 25%、深さ 60 はいずれも検証対象で、固定値ではない。

### 3.3 局面評価

サイド差・HP・場のポケモン数・手札枚数に加えて、

- 今ターン攻撃できるか / きぜつを取れるか / 次ターンも攻撃を継続できるか
- 次ターンに相手からきぜつさせられる可能性
- 後続アタッカーの準備、オーロンゲ ex への進化経路、Punk Up を活かせるか
- 有効なエネルギーがどこに何枚あるか
- 自分が勝つまでの攻撃回数 / 相手が勝つまでの攻撃回数
- ベンチに取りやすいサイドを置いていないか
- 手札枚数ではなく、使用可能なカードがあるか

終局を ±1 とするなら、中間評価は必ずその内側に収める。

## 4. 相手モデル

### 4.1 デッキタイプを確率分布で持つ

手札を一枚単位で当てにいかない。公開カードからデッキタイプの分布を保ち、必ず unknown を残す。
場のポケモン、専用カード、エネルギーの種類、トラッシュ、進化ライン、
「使えたはずのカードを使わなかった」という弱い証拠を使う。汎用カードは強い証拠にしない。

### 4.2 反映先

固定行動を命令するためではなく、`Searcher.begin()` に渡す相手デッキ、相手側のロールアウト方策、
打ち切り評価、対象の優先度、根の事前評価に反映する。複数候補があれば加重平均する。

    Q(a) = Σ_d P(d|O) Q(a,d)

仮説を増やすと各候補の標本が減るので、初期は上位 2 デッキ + unknown に絞る。

### 4.3 実装前の Oracle 実験

推定器を作る前に、正解の相手デッキを与えて上限を測る。

- **Baseline** — 相手も自分と同じデッキだと仮定 (現状)
- **Oracle Deck** — 正しい相手デッキを探索へ渡す
- **Oracle Strategy** — 正しいデッキと対面別方策を与える

Oracle でも強くならないなら、推定を実装する意味は薄い。先に対面戦略か反映方法を直す。

## 5. 学習相手

### 5.1 軸を 4 つに分ける

構築だけで多様性を作らない。デッキ構築 (標準 / 攻撃寄り / 安定重視 / 妨害採用)、
プレイ方針 (標準 / 攻撃 / 準備 / 妨害 / 安全 / 終盤重視)、探索強度 (ルールのみ / 短時間 / 十分)、
ランダム性 (ほぼ決定的 / 少量 / 多様) を組み合わせる。同じコードで、設定ファイルだけ変える。

    {"deck_profile": "deck_A", "strategy_profile": "aggressive",
     "attack_weight": 1.2, "setup_weight": 0.8, "resource_weight": 0.5, "random_rate": 0.15}

### 5.2 初期リーグ

主要デッキ 3 種 × プレイ方針 2 種 = 6 体。これに現行提出版、過去最強版、ランダム、
学習に使っていない未知構築を加えて 9〜10 体。弱い相手を量産するより、各デッキの勝ち筋を
実行できる相手を少数作る。

### 5.3 過去版をリーグへ追加する

リーグを上回った版を保存し、以後の相手に加える。古い相手だけを攻略する過適合を防ぐ。

    champion_001 / champion_002 / current_submission / candidate

## 6. 学習用と評価用の分離

同じ相手で調整し続けると条件を暗記する。シードが使えないため、**デッキと方策プロファイルで**分ける。

- **学習・調整用** — 主要デッキの標準構築、既知の方策プロファイル
- **検証用** — 別構築、学習に使っていない方策設定
- **最終評価用** — 現行提出版、過去最強版、未知構築、未使用の相手方策、Kaggle 相当の時間予算、先後入れ替え

最終評価セットを見ながら重みを調整してはいけない。調整に使った時点で検証用ではなくなる。

## 7. Colab

CPU 処理なので、CUDA を使わない限り GPU を割り当てても速くならない。まず CPU ランタイムを使う。
無料枠の資源は保証されないため、長時間ジョブは途中終了を前提に設計する。

### 7.1 役割分担

- **Mac** — コード修正、単体テスト、局面の再現、10〜20 戦の動作確認、ログの目視
- **Colab CPU** — 大量 A/B、対面別勝率、重み探索、Oracle 実験、複数条件評価、敗因ログ収集
- **Kaggle 相当環境** — 最終候補のみ。時間予算と提出物の動作確認

### 7.2 ジョブは小分けに

1 バッチ 50〜100 戦。1 戦ごとに結果を追記保存し、バッチ終了時に集計を保存する。
再開は未完了の対戦番号から。結果は Google Drive へ定期保存する (ランタイム内だけだと切断で消える)。

### 7.3 並列実行

`Searcher` はプロセスごとにエンジン状態を持つので、スレッドではなくプロセス並列。

**戦/時だけで判断してはいけない。** 思考時間は壁時計で切っているため、コア数を超えて
プロセスを詰め込んでも 1 戦の所要時間はあまり延びず、代わりに各エージェントが同じ時間で
回せるロールアウト数が減る。戦/時は上がるが、エージェントは弱くなる。

実測 (Colab CPU 2 コア) では、並列 4 が 142 戦/時で最良に見えたが、これは 1 手あたりの
思考量を半分に落として数をこなしていただけだった。

判断基準は **1 手あたりのロールアウト数を並列 1 の 90% 以上に保った上での戦/時**とする。
`tools/bench.py` が PTCG_TRACE から両方を測る。

機械が違うと同じ `PTCG_MAX_SLICE` でもロールアウト数が変わるため、Mac と Colab の結果を
直接比べるには、ロールアウト数が揃うようにスライスを機械ごとに較正する必要がある。

### 7.5 較正の実測 (2026-08-03)

1 手あたりのロールアウト数。スライスは 0.58 秒。

    Mac (8 論理 CPU)          Colab (2 vCPU)
      並列1  511  100%          並列1  135  100%
      並列2  343   67%          並列2   53   39%
      並列4  250   49%
      並列6  295   58%

Colab は 2 vCPU といっても実質 1 コア相当で、並列 2 にすると戦/時が増えないまま思考量が
6 割落ちる。**Colab では並列 1 しか選べない。**

1 戦の所要時間が Mac 46.6 秒 / Colab 48.6 秒とほぼ同じなのは、思考時間を壁時計で
切っているためである。CPU の速さは 1 戦の時間ではなくロールアウト数に出る。
**Colab のコアは Mac の約 3.8 倍遅い。**

Kaggle 本番はこの Mac の約 8.6 倍遅い。本番の 5 秒スライスで得られるロールアウト数は
511 × (5.0/0.58) ÷ 8.6 ≒ 510 なので、**Mac・並列 1・スライス 0.58 秒がほぼちょうど
Kaggle 相当**になる。Colab で同じ思考量にするにはスライス 2.2 秒が必要で、約 20 戦/時まで落ちる。

| 用途 | 環境 | スライス | 速度 | 思考量 |
|---|---|---|---|---|
| 高速スクリーニング | Mac 並列6 | 0.58 | 約290 戦/時 | Kaggle の約6割 |
| 最終評価 (提出判断) | Mac 並列1 | 0.58 | 約77 戦/時 | Kaggle 相当 |
| 長時間の放置実行 | Colab 並列1 | 2.2 | 約20 戦/時 | Kaggle 相当 |

スクリーニングで思考量が 6 割でも、両者に同じ条件がかかるので A/B の比較は公平である。
ただし絶対値は本番と違う。提出を判断する最終評価は並列 1 で取り直すこと。

### 7.4 実験の三段階

- **高速スクリーニング** — 20〜40 戦、短い時間予算。明らかに弱い変更を除外する
- **中間評価** — 100〜300 戦、本番より短い予算。対面別の傾向を見る
- **最終評価** — Kaggle 相当の予算、主要対面ごとに十分な試合数、先後入れ替え、現行版と過去最強版と未知構築

## 8. 保存するログ

対戦ごと: 実験 ID、コミット ID、両者のエージェント名・設定・デッキ、先後、勝敗、総手数、
実行時間、タイムアウト、例外、推定した相手デッキと確率の推移。
(乱数シードは保存しても再現できないので、再現性はこのログ自体で担保する)

意思決定ごと: 局面フェーズ、`select.context`、各候補のカード ID と行動型、ルール評価、
探索回数、平均評価、評価分散、UCB 値、最終選択、最多試行候補、最高平均評価候補。

## 9. 評価指標

勝率だけでは改善点を特定できない。

**基本動作** — オーロンゲ ex 成立率、成立までの手数、Punk Up の有効使用率、攻撃開始までの手数、
攻撃可能なのに攻撃しなかった割合、きぜつを逃した割合、重要カードの誤廃棄率、不要なベンチ展開率、後続準備率

**探索品質** — 1 候補あたり試行回数、候補評価の標準誤差、最多試行候補と最高平均評価候補の一致率、
打ち切り評価と最終勝敗の相関、探索評価が正なのに負けた割合、候補差が小さい局面の割合

**対面適応** — デッキ分類の精度、正解が上位候補に入る割合、推定が安定するターン、
Oracle との勝率差、誤分類時の勝率、unknown 時の勝率

**運用** — 平均 / 最大思考時間、タイムアウト率、例外率、フォールバック率、Kaggle 換算の総使用時間

## 10. ロードマップ

1. **基礎方策の安定化** — 文脈の分類、未知文脈で価値表を無効化、フェーズ管理、代表局面テスト 100 件、敗因分類
2. **探索と評価** — ルール評価を根の事前値へ、勝ち筋に近い局面評価、打ち切り深さの比較、UCB 最終選択基準、早期終了
3. **相手リーグ** — 主要 3 デッキ、各 2 方針、現行版と過去最強版、学習/検証/最終の分割、Colab で自動化
4. **相手デッキ情報** — Oracle 実験、対面別ルールの有効性、`enemy_deck` へ正解を渡す、公開カードから確率更新、フェイルセーフ
5. **重み調整** — 複数設定で探索、学習リーグの勝率と中間指標、検証リーグで過適合確認、打ち切り評価の誤差から重み調整、新champion を追加
6. **機械学習** — 局面ログが十分に溜まった後に限る。学習部分のみ GPU、対戦生成は CPU

## 11. 提出の節目

### 11.1 いつ出すか

ロードマップのフェーズが一つ完了した時点、および現 champion を明確に上回った時点で提出する。
思いつきでは出さない。提出枠は 1 日 5 回しかなく、ラダーのスコアは相手の分布に依存するため、
細かい差を提出で確かめようとすると枠だけ消える。

提出の条件は次の 3 つをすべて満たすことである。

1. **最終評価セットで現 champion に勝つ** — Kaggle 相当の時間予算、先後入れ替え、n ≥ 200。
   勝率が 57% 以上 (z > 2) であること。50% 近辺なら出さない
2. **時間予算の確認を通過する** — 最大スライスが上限を超えず、Kaggle 換算の総使用時間が
   600 秒に対して余裕を残すこと
3. **提出物の自己対戦検証が DONE で終わる** — `tools/build_submission.py` の検証を通すこと

### 11.2 champion の凍結

`submission.tar.gz` はビルド時点の `shared/*.py` を同梱した自己完結アーカイブである。
後から共有コードを変えても中身は変わらないので、これがそのまま過去バージョンの凍結物になる。

    champions/<score>/submission.tar.gz   提出したもの
    champions/<score>/meta.json           スコア、日時、コミット ID、デッキ、備考
    champions/<score>/agent/              展開したもの。そのまま対戦相手に使える

過去バージョンと現行版は同じプロセスで動くため、`policy` `search` といったモジュール名を
奪い合う。`main.py` の `_load_shared()` が、自分のディレクトリにある実体を自分専用の名前で
読み込むことでこれを避けている。他のエージェントのディレクトリ (`deck.csv` がある場所) は
探索候補から外す。凍結した古い `main.py` が `sys.path` の先頭に自分を差し込むためである。

## 原則

- ルールベースは基本動作と探索の事前知識を担う
- 探索は局面固有の例外を判断する
- 相手情報は固定命令ではなく、探索する未来を現実に近づけるために使う
- 相手デッキを一つに早期確定しない
- 学習相手は複数構築・複数方策・複数強度で構成する
- 学習用と最終評価用の相手を分離する
- 直交する変更はまとめてよいが、疑わしいものと副作用が読めないものは分けて A/B する
- 勝率だけでなく局面別の失敗率を測る
- 大量対戦は Colab の CPU 上で小分けに実行する
- すべての実験をコミット ID と設定まで含めて追跡可能にする

到達目標は、相手の手札を高度に予測することではない。オーロンゲデッキの基本的な勝ち筋を
安定して実行し、複数の主要デッキと異なる相手方策に対して、局面に応じた例外判断ができる状態である。
